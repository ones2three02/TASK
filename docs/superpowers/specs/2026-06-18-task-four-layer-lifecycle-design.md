# TASK 四层个人企业级全生命周期管控设计

## 1. 背景

TASK 当前采用四层结构：

- T - Target：目标与里程碑。
- A - Action：行动看板。
- S - Serve：服务与交付价值。
- K - Keep：资产沉淀与复盘。

现有能力已经能完成基本项目规划，但 Serve 更偏“事后交付记录”，无法在项目启动时先规划交付物、验收标准和交付证据。用户希望仍然只保留 T/A/S/K 四层，但让工具达到个人使用场景下的企业级项目交付标准。

## 2. 设计目标

本次设计目标：

- 不新增第五个主模块，继续保持 T/A/S/K 四层认知模型。
- 将 S 从“事后总结”升级为“交付计划与验收中枢”。
- 让 A 围绕 S 推进，行动最好能关联交付项，但不强制。
- 让 K 承接证据、版本、文档、复盘和项目快照。
- 通过 Dashboard 智能提醒阶段缺项，但不强制阻断个人工作流。
- 让 AI 拆解能力输出更完整的 T/A/S/K 初始规划。

## 3. 非目标

第一版不做以下内容：

- 不做多人账号、权限、审批流。
- 不做复杂甘特图、工时、资源排期。
- 不做企业 IM 通知、飞书/企微推送。
- 不做云端文件资产库。
- 不新增独立 Deliverable 主导航。

这些可以作为后续增强，不进入本轮核心设计。

## 4. 四层职责重定义

### 4.1 T - Target：项目章程

Target 不只是目标名称，而是项目立项和边界定义。

建议增强字段：

- 项目目标：项目要达成的业务或工作结果。
- 背景说明：为什么要做。
- 范围说明：本项目包含什么。
- 非范围说明：本项目明确不做什么。
- 成功标准：做到什么程度算成功。
- 里程碑：关键路径节点。
- 风险假设：启动阶段已知风险或前提。

企业级价值：

- 避免项目边界模糊。
- 为后续 Action 和 Serve 提供判断依据。
- 让 AI 拆解结果不只是待办，而是带目标口径。

### 4.2 A - Action：执行控制

Action 继续保持看板体验，但增强为执行控制面。

建议增强字段：

- 行动标题、说明、优先级、截止日期、状态。
- 关联 Serve 交付项，建议关联但不强制。
- 阻塞状态：正常、阻塞、存在风险。
- 阻塞原因：说明当前卡点。
- 完成证据：链接、说明或简短记录。

企业级价值：

- 行动不再是孤立待办，而是能追溯到交付项。
- 临时调研、沟通、修复任务仍然可以不关联 Serve，保持个人工具灵活度。
- Dashboard 可以提示“未归属行动”“已逾期行动”“存在阻塞行动”。

### 4.3 S - Serve：交付计划与验收

Serve 是本次设计的核心。它不再只是项目完成后的总结，而是从项目规划阶段就创建的交付中枢。

建议增强字段：

- 服务对象/需求方：为谁交付。
- 交付物名称：要交付什么。
- 交付物说明：交付物范围和内容。
- 计划交付日期：期望交付时间。
- 实际交付日期：真实交付时间。
- 交付状态：规划中、交付中、已交付、已验收、需返工。
- 验收状态：待验收、验收通过、需调整。
- 验收清单：可勾选 checklist。
- 返工项：验收未通过时记录需要调整的内容。
- 交付证据：链接、版本号、截图说明、文档位置或其他证据。

验收清单示例：

- 核心功能已完成。
- 关键字段已校验。
- 异常场景已处理。
- 文档已补充。
- 需求方已确认。

企业级价值：

- 交付前有计划。
- 执行中能追踪。
- 交付后有验收依据。
- 返工和证据不会散落在备注里。

### 4.4 K - Keep：资产沉淀与复盘

Keep 保持资产沉淀定位，但增强为项目最终可追溯资料库。

建议增强字段：

- 资产名称。
- 资产类型：文档、链接、归档包、交付证据、版本记录、复盘。
- 内容或链接。
- 关联 Serve 交付项，可选。
- 关联 Action，可选。
- 创建时间。

企业级价值：

- 项目结束后能追溯交付结果。
- 可生成复盘文档。
- 可导出项目快照。
- 形成可复用的个人项目知识库。

## 5. 阶段门策略

采用“智能提醒，允许跳过”。

系统不会阻断用户进入下一阶段，但会提示缺失内容。例如：

- 没有 Target：建议先建立项目目标和成功标准。
- 有 Target 但没有 Serve：建议先规划交付物和验收清单。
- 有 Serve 但没有 Action：建议围绕交付项拆解行动。
- 有 Action 但未关联 Serve：提示存在未归属行动。
- 有已交付 Serve 但没有验收清单完成：提示补充验收。
- 有已验收 Serve 但没有 Keep：提示归档交付证据和复盘。

该策略适合个人工具：既有企业级标准，又不让流程卡死。

## 6. AI 拆解能力

AI 需求拆解应从当前 Target/Action 扩展为完整 T/A/S/K 初始规划。

输入：

- 用户输入的需求文本。
- 用户上传的参考资料文本。

输出建议结构：

- targets：目标、描述、里程碑、成功标准。
- actions：行动、描述、优先级、建议截止、可选关联交付项。
- serves：服务对象、交付物、说明、计划日期、验收清单。
- keeps：建议沉淀的文档、链接、交付证据和复盘材料。
- risks：可作为 Target 风险假设或 Action 阻塞提示的风险项。

导入体验：

- 预览页仍按四层展示。
- 用户可以勾选导入哪些 Target、Action、Serve、Keep。
- Action 关联 Serve 时，如果对应 Serve 未导入，则自动取消关联或提示用户。

## 7. 页面与交互

### 7.1 Dashboard

Dashboard 应展示项目健康度：

- Target 完整度。
- Action 完成率。
- Serve 交付/验收进度。
- Keep 归档完整度。
- 风险和阻塞数量。
- 下一步建议。

质量门提示使用非阻断卡片，例如：

- “当前有 2 个交付项没有验收清单。”
- “当前有 3 个行动未关联交付项。”
- “交付项已验收，但还没有归档证据到 Keep。”

### 7.2 Target 页面

增强目标表单和展示：

- 增加范围、非范围、成功标准、风险假设。
- 里程碑继续可勾选。
- 目标卡片展示成功标准摘要。

### 7.3 Action 页面

增强行动卡片：

- 支持选择关联 Serve。
- 支持阻塞状态和阻塞原因。
- 支持完成证据输入。
- 筛选器增加“未关联交付项”“阻塞中”。

### 7.4 Serve 页面

Serve 页面从“服务价值”升级为“交付计划与验收”。

核心区域：

- 交付项列表。
- 交付状态。
- 验收状态。
- 验收清单完成度。
- 交付证据。
- 返工项。

交付状态建议：

- draft：规划中。
- active：交付中。
- delivered：已交付。
- accepted：已验收。
- changes_requested：需返工。

为兼容现有数据，可保留旧状态并在 UI 层映射，或做一次轻量迁移。

### 7.5 Keep 页面

增强资产类型和关联能力：

- 新增交付证据、版本记录、复盘类型。
- 可从 Serve 一键沉淀到 Keep。
- 复盘文档包含 Target、Action、Serve、Keep 四层完整摘要。

## 8. 数据模型兼容策略

现有 localStorage 数据必须兼容。

原则：

- 新字段全部可选，并在加载时补默认值。
- 不破坏已有 Target、Action、Serve、Keep 数据。
- 项目导出快照升级版本号，例如从 `version: 1` 到 `version: 2`。
- 导入旧快照时自动补齐新增字段。

建议新增字段：

- Target：`scope`、`outOfScope`、`successCriteria`、`risks`。
- Action：`serveId`、`blocked`、`blockerReason`、`evidence`。
- Serve：`plannedAt`、`acceptanceChecklist`、`evidence`、`reworkItems`。
- Keep：`relatedServeId`、`relatedActionId`，并扩展 `type`。

## 9. 测试策略

必须覆盖：

- 旧数据加载兼容。
- 新字段默认值补齐。
- 项目快照导出/导入版本兼容。
- Dashboard 阶段门提示逻辑。
- AI 解析输出包含完整 T/A/S/K。
- Action 关联 Serve 的边界情况。
- Serve 验收清单完成度统计。

## 10. 分阶段实施建议

### 阶段一：数据模型与规划能力

- 扩展 Task 数据结构。
- 增强 taskPlanning 统计与推荐逻辑。
- 增强 AI 拆解输出 T/A/S/K。
- 更新测试。

### 阶段二：Serve 前置交付计划

- 重做 Serve 表单和卡片。
- 增加验收清单、交付证据、返工项。
- 支持从 Serve 沉淀 Keep。

### 阶段三：Action 执行管控

- 增加关联 Serve。
- 增加阻塞状态和完成证据。
- 增加筛选器和卡片提示。

### 阶段四：Dashboard 质量门

- 展示项目健康度。
- 展示智能提醒。
- 输出下一步建议。

### 阶段五：复盘与导出

- 升级复盘文档。
- 升级项目快照导出/导入。
- 补充版本兼容测试。

## 11. 设计结论

确认方案：

- 保留 T/A/S/K 四层，不新增独立 Deliverable 层。
- 将 S 前置为交付计划与验收中枢。
- Action 建议关联 Serve，但不强制。
- 阶段门采用智能提醒，允许跳过。
- AI 应一次性生成 T/A/S/K 初始规划。
- 第一版面向个人全生命周期管控，不做团队权限和审批流。
